# Generic compute provider runtime

This internal assembly is independent of Core's database, application services and agent SDK. CSweet.Compute.Contracts carries the shared protocol and purpose-specific signature encoding. Neither assembly is published as a package yet.

## Dispatch and payload verification

ComputeDispatchVerifier checks pinned Core signatures, enrollment/scope, expiry, specification/template digests, composed grants and local capabilities. Certified metadata must come from protected deployment configuration, never a workload-supplied dictionary or filename. ComputeImageCertificationVerifier separately checks release evidence under a pinned release key and purpose. ComputeCertifiedPayload requires exact installed runtime-file coverage, protected paths and matching SHA-256 content for the image and every declared payload file. Retained handles deny write/delete sharing until disposal and must stay alive while consuming the files. These verifiers do not execute a certification suite or establish that any deployment passed it.

## Durable execution and physical accounting

ComputeReplayJournal uses an exclusive cross-process lock and flushed atomic state replacement. Provisioning reserves environment count and aggregate CPU/memory/disk/GPU in the same snapshot as the execution claim. Capacity is installer-configured allocatable capacity after host/platform overhead; it is not live hardware inventory. Failure, stop and unconfirmed destroy retain reservations. Exact replays observe instead of repeating provisioning; generation fences and destroy intent prevent stale activation or resurrection.

RunPhysicalAsync passes the recorded provider resource ID to the trusted backend. A returned ID must have verified physical ownership; the journal persists it before returning and rejects replacement by a dispatch or later callback. Known identity is saved even if cancellation arrives after the backend completes. A crash before identity persistence still requires fenced orphan discovery, never blind recreation. Activation requires both a reservation and a recorded ID. Callbacks must await owned helper termination before releasing the journal lock. Hypervisor jobs that outlive a helper need separate fenced inventory/quiescence checks.

Production paths require Windows SYSTEM/administrator ownership, protected ACLs and no links in the path or ancestors. The installer explicitly initializes a fresh journal; ordinary runtime reads and the monitor never recreate missing/corrupt history. Test-only internal path guards exercise mechanics in temporary directories. The unpublished journal envelope is version 4; versions 1, 2 and 3 are rejected rather than inventing resource accounting, grant attribution or result sequencing, or resetting history. No deployed journal was migrated. Non-test older history requires explicit inventory-backed migration.

## Lease enforcement and resident recovery

EnforceExpiredLeaseAsync derives local authority from original protected provisioning terms, without a fresh Core connection or agent request. It persists expiry and an attempt before invoking cleanup under the journal lock. Ephemeral expiry selects destroy; persistent expiry selects stop and never authorizes disk deletion. The expired fence survives failed cleanup, restart and subsequent clock rollback. Fresh activation cannot override the stored expired lease; explicit renewal is future work. Exact-owned stop/destroy may repeat to recover unknown outcomes. After a confirmed cleanup, the Hyper-V executor re-observes the exact-owned VM under the journal lock. An unchanged stopped/absent state performs no further mutation and leaves the journal bytes and outbox unchanged. Drift triggers a new attributed cleanup attempt; inventory errors propagate rather than imply absence. Beginning a new attempt clears the old confirmation, including when clock time has not advanced. Physical confirmation does not release capacity or persistent storage.

ComputeLeaseMonitor performs a startup scan, pages through at most 100 reservations per read, and rechecks each due lease through the enforcer. A bounded channel coalesces wake hints. The next future expiry schedules a timer, with recovery at most every 30 seconds between passes for missed wakes, reconnect and failures. Slow physical cleanup adds to the scan duration; this is not a hard real-time expiry bound. One expected per-workload failure does not starve other leases. Diagnostics contain bounded environment IDs and counts, not raw exception text. Missing/corrupt history or unexpected faults terminate the monitor for service supervision rather than reset it.

The Hyper-V executor can attach one monitor and signals it after journal-backed dispatches, including failures that may leave a reservation. The service host must run and supervise the monitor, report its diagnostics and restart it after recoverable process failure. No provider service is installed or started by this checkpoint.

## Offline maintenance evidence

Reservations retain their original provisioning operation and grant references. Lease enforcement queues a Requested event atomically with its expiry fence, before the physical callback. Physical observations or fixed-code failures are queued with the corresponding state change afterward. A failed post-effect result write retains the original request; it does not invent a physical failure. Events include immutable IDs, scope, original grant attribution, generation, lease/persistence terms, action, attempt and timestamp. They are evidence, not new grants or complete storage-teardown assertions.

ComputeMaintenanceOutboxDispatcher reads up to 100 events, releases the journal lock during delivery and removes each entry only after acknowledgement of its exact digest. Lost acknowledgements replay the same event ID and bytes after restart. The receiver must authenticate the provider and deduplicate that ID. Delivery and acknowledgement never release resource reservations. ComputeMaintenanceSigner now uses an enrolled P-256 certificate to sign a short-lived delivery envelope containing unchanged historical event bytes and their digest. Core verifies the distinct maintenance signature purpose and current node enrollment, then checks original provisioning operation/grants, scope, placement, generation, specification and lease terms before appending to the sealed audit ledger. Fresh envelopes can deliver old offline evidence without changing its event identity. Current agent disable/grant revocation does not invalidate attribution to previously granted cleanup terms. The Core HTTPS endpoint and ComputeMaintenanceHttpClient are implemented and tested over loopback TLS. The client disables redirects/cookies/default credentials, bounds the full operation and acknowledgement size, and requires the matching event ID/digest. ComputeMaintenanceDeliveryWorker recovers the outbox on startup, coalesces wake hints and scans at least every 30 seconds between passes. It retries transport failures with exponential backoff from one to 60 seconds, which wake hints cannot bypass. Each batch is bounded to 100 events; full batches are paced. Lost acknowledgements retain identical evidence for retry. Cancellation interrupts delivery without acknowledging the pending row. Journal read/acknowledgement failures escape to service supervision. Run the worker independently of lease enforcement so Core outages do not block expiry cleanup. The Hyper-V executor can attach one delivery worker and wakes it after lease enforcement, including uncertain failures that leave durable evidence; timer recovery still covers missed wakes. ComputeProviderMaintenanceSupervisor runs delivery separately from the lease monitor. Its awaitable DeliveryFailure signal reports a stopped delivery lane without cancelling local expiry enforcement. A lease-monitor fault propagates to the owning service and cancels delivery; shutdown awaits transport exit before dependencies may be disposed. Each supervisor represents one service lifetime. The owner must observe both RunAsync and DeliveryFailure, diagnose faults, and preserve lease enforcement while repairing delivery. The protected enrollment loader and exact OS-certificate selection are implemented; Windows service installation and concrete startup/recovery composition remain pending.

The journal has a bounded storage budget and fails writes when exhausted. Confirmed, physically unchanged recovery no longer grows the outbox, but repeated uncertain cleanup or physical drift still can. Queue retention/backpressure and reserved space for expiry cleanup must be validated before deployment so a prolonged delivery outage cannot prevent required cleanup. This checkpoint does not establish that offline storage sizing guarantee.

## Provider enrollment configuration

ComputeProviderConfigurationLoader reads version 1 installer-owned JSON, limited to 64 KiB, using the strict shared JSON protocol. It checks the configuration file and both runtime roots with WindowsComputeProtectedPaths. Journal and workload directories must be absolute, protected, separate roots; configuration must be outside both. Fields carry organization/node/provider enrollment, pinned Core and node P-256 public identities, a Core HTTPS origin, allocatable capacity, and an exact certificate thumbprint plus CurrentUser or LocalMachine My store location. Unknown fields, embedded endpoint credentials, nested roots, invalid scope and invalid public keys fail before composition. No private key is supplied in configuration.

ReadAsync does not open delivery credentials. Start local journal-backed lease recovery independently, then use OpenSigningCertificate to open the uniquely matched, current, accessible P-256 certificate whose public key equals the enrolled node identity. The caller owns the returned certificate and must dispose it only after maintenance delivery exits. Certificate selection requires validity through a full two-minute envelope; ComputeMaintenanceSigner repeats this check on every signature. The Hyper-V host retries access to the same configured credential with bounded backoff, disposes an invalid cached signing connection, and reports delivery recovery. Certificate rotation still needs explicit enrollment/configuration and service recovery; there is no arbitrary-certificate fallback, automatic key creation or private-key export. Tests exercise selection with in-memory certificates and path validation through an injected guard; actual service-account certificate permissions and protected installation still require deployment validation.
## Remaining deployment work

ListReservationsAsync is bounded privileged recovery discovery, not an agent API or an execution grant. Service composition/installation, concrete service configuration and recovery policy, desired-state provision/boot completion, guest execution, asynchronous hypervisor-job fencing, confirmed storage cleanup and reservation release remain required. A Missing VM observation never proves complete teardown. Real VM isolation, installation and crash/orphan recovery still require hardware acceptance tests.
### Lifecycle result transport

`ComputeResultHttpClient` delivers an already signed observation to the configured Core HTTPS origin. It preserves the payload and signature across retries and returns only an acknowledgement matching operation ID, sequence and payload digest. An unchanged/superseded result can be acknowledged with `Applied = false`; this does not prove the requested physical state. The production handler uses normal TLS validation without redirects, cookies or default credentials. Requests and responses are bounded and the entire delivery has a 30-second cancellation deadline.

This client does not refresh expired observations, maintain a durable queue or allocate sequence numbers. Those must be integrated with protected journal observations and recovery before the provider becomes operational. Retry after a lost Core response is covered using the actual reconciler behind a simulated HTTP handler; this is not physical-provider acceptance.

### Durable lifecycle observations

Journal version 4 accepts trusted `ComputeLifecycleObservation` evidence returned by a physical backend and commits its resource identity, monotonic operation sequence and latest pending result atomically. `ListResultsAsync` provides bounded recovery reads. `AcknowledgeResultAsync` removes only the matching operation/sequence/digest; an acknowledgement for an older replaced observation leaves the newer row intact. Acknowledgement does not release reservations or reset sequence history.

Cancellation after a successful effect does not discard its completed observation. If its commit fails, the pre-effect execution fence remains and recovery must observe physical ownership before queuing new evidence. The Hyper-V executor supplies conservative observations and never translates raw VM absence into confirmed disk teardown or raw running state into guest readiness.

Results expire two minutes after observation. Reads do not renew them. Delivery-worker composition and authorized recovery of expired evidence remain pending; result discovery alone is not a running delivery service. Only the latest observation per operation is pending, while sequence history is retained. This does not yet guarantee cleanup storage capacity through an arbitrarily long offline period.

`ComputeResultOutboxDispatcher` performs one bounded delivery pass outside the physical journal lock. Its operation-ID cursor traverses at most 100 rows at a time, including past expired observations. Expired rows remain unchanged and are returned in `RequiresObservation`; they do not grant authority to execute, renew or observe a workload. Callers must complete the cursor sweep and restart discovery to recover newly inserted lower IDs. Transport failures leave rows pending; retry from the previous cursor remains safe. Production scheduling, signing/client composition and authorized expired-observation recovery remain pending.

`ComputeResultDeliveryWorker` supplies startup discovery, bounded wake hints, fallback discovery and paced cursor sweeps for the result dispatcher. Transport failures retain the previous cursor and use capped exponential backoff; journal or configuration faults escape to the host. Cancellation retains any unacknowledged row. Its report includes bounded expired evidence requiring observation authority. The worker is not yet wired into `HyperVMaintenanceHost`; certificate/client ownership, supervisor integration, executor wakes and authorized expiry recovery remain pending.

The provider maintenance supervisor now optionally runs result delivery as an independent lane, with a separate `ResultDeliveryFailure` signal. A stopped delivery lane does not stop local lease enforcement. Shutdown cancels and joins both delivery workers before the owner disposes dependencies. `HyperVMaintenanceHost` composes this lane with its own enrolled signing certificate and HTTPS client; executor result changes provide wake hints. Reports of expired evidence are diagnostic only and do not authorize new physical observations. Fresh-observation recovery and installed-service/hardware acceptance remain unfinished.

### Provider work client

`ComputeProviderWorkSigner` issues one-minute purpose-separated node proofs for discovery or a single claim. `ComputeWorkHttpClient` uses the configured HTTPS origin, bounded responses and a 30-second request deadline without redirects, cookies or default credentials. Discovery pages are hints and must have distinct ordered IDs and a consistent cursor. Every returned dispatch is independently verified against enrollment and the requested operation. Physical execution must verify the packet again because its authority may expire after delivery.

Owned credential recovery, work-worker/wake composition, fresh-observation recovery and real HTTP/provider acceptance are still pending. The current client tests use actual Core work services behind a simulated HTTP handler.

`ComputeObservationRecovery` performs a bounded, two-minute recovery pass for expired pending results. It obtains fresh Core claims and accepts only verified observation authority for the exact queued operation and scope. The executor then verifies again and reads physical state under its journal fence, producing a new result sequence. Fresh evidence needs no claim; unavailable claims leave expired evidence intact. The pass is not yet host-scheduled, and terminal/superseded evidence retirement still needs explicit handling.

Observation recovery is now composed in `HyperVMaintenanceHost`. A separate owned work connection obtains fresh signed claims, expired-result reports provide wake hints, and startup/fallback recovery covers missed notifications. The supervisor exposes `ObservationRecoveryFailure`, keeps lease cleanup running when recovery stops, and joins all workers before connection disposal. This remains maintenance/observation-only: no fresh provisioning dispatch loop or certified template resolver is enabled. Terminal evidence retirement and real-network/hardware acceptance remain incomplete.

Host-composed recovery now checks exact recorded receipts before requesting new observation authority. The same owned work connection handles receipt reads and claims sequentially. A matching receipt removes only its exact pending row and never touches physical state or reservations; unavailable receipt transport retries with backoff, and an absent receipt falls through to authorized observation. Unrecorded superseded/terminal evidence still requires explicit disposition support.

## Installed template catalog

ComputeTemplateCatalog reads a separate protected version-1 JSON document containing Templates entries, each with Template, ImagePath and Certification. It accepts at most 16 entries and 1 MiB; IDs must be unique. Image paths must be absolute and administrator protected. The caller supplies the pinned release public key, provider ID/version, runtime directory and complete installed runtime-file manifest separately. None of these settings comes from an agent dispatch. Certification must match the provider release, requested template and exact runtime-file set.

Use the detached Templates dictionary to configure the dispatch verifier and OpenAsync as the executor's payload resolver. Every open rechecks certification expiry and verifies/locks actual image and runtime bytes through ComputeCertifiedPayload. Loading catalog metadata alone does not certify current file contents. The maintenance-only service still has no template catalog configured; initial provisioning intake must explicitly compose it without making local lease cleanup depend on catalog availability. No catalog, certificate or VM image has been installed by this change.
## Bounded dispatch intake

ComputeDispatchIntake.RunOnceAsync consumes one ordered discovery page of at most 100 operation IDs under a two-minute pass deadline. Discovery is only a hint: each ID needs a separate current claim, independent dispatch verification and an exact operation-ID match. The verified specification/template snapshot is passed to the executor without changing Execute or Observe mode. Null claims are deferred. Journal, authority and physical failures propagate rather than being reported as completed work; the caller must retain recovery behavior. Full pages return their cursor for the next pass. The pass is intended for durable work wakeups and bounded startup/reconnect discovery, not an agent polling loop.

HyperVWorkConnection now exposes authenticated discovery using its existing pinned credential and HTTPS transport. A service intake lane and durable work notification subscription still need composition; maintenance remains unchanged and must remain available during intake outages.
ComputeDispatchIntakeWorker supplies coalesced wake handling around the bounded pass. It scans on startup, after hints and during bounded reconnect recovery; full pages are paced at one second. Discovery/claim transport outages retry with capped 1–60-second backoff that hints cannot bypass. Authority and executor/journal failures stop the lane. ComputeProviderMaintenanceSupervisor accepts an optional intake worker, exposes DispatchIntakeFailure and joins it during shutdown while keeping local lease enforcement independent. Production catalog/settings and durable notification transport still require host composition; the maintenance entry point has not been enabled for provisioning.
## Optional provisioning settings

Provider configuration version 1 accepts an optional provisioningSettingsPath. Omit it for maintenance only. When present, it must name a separate protected absolute JSON file outside journal/workload roots. Its version-1 fields are catalogPath, releasePublicKey, providerVersion, runtimeDirectory and runtimeFiles (the complete installed file-name set). The settings, catalog and runtime directory must be protected; metadata cannot reside under mutable journal/workload roots. No private key is stored in these files.

The host loads the catalog at startup and enables authenticated intake using the enrolled Core endpoint and the existing node certificate. The initial Hyper-V composition advertises lifecycle actions, isolated no-network templates, no GPU assignment and persistent preservation. All request constraints still undergo dispatch verification. Missing, rejected or malformed settings emit provisioning-configuration-unavailable and leave maintenance running with no provisioning authority. Fixing installed settings requires restarting the process; no hot reload or alternate-key fallback is implemented. Cancellation is propagated. No settings or certified images have been installed by this development work.
