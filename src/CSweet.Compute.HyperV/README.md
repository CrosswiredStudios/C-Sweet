# Generic Hyper-V compute backend

This internal assembly extracts VM mechanics from the retired WebHost proof of concept. It is not registered as an operational provider yet. Agents cannot call its driver or supply host paths, PowerShell scripts, VM IDs or ownership markers.

The initial driver supports x64 Windows and Linux, a standalone certified VHDX copied to one private OS disk, static memory and CPU limits, and no network adapter or GPU. Creation leaves the VM stopped. There is no Docker, web application, artifact ISO or mandatory scratch-disk requirement. Unsupported specifications fail before invoking a helper. Expanding the virtual disk does not expand a guest partition; image preparation and guest readiness remain separate work.

Control and observation require the exact persisted hypervisor ID and a matching node/organization/installation/environment ownership marker. Inventory errors fail rather than proving absence. Stop preserves disks. Destroy unregisters the VM but does not remove its disk or certify teardown. Only later protected storage/orphan reconciliation may release reservations. Cancellation kills the owned helper and waits for exit; this does not prove that an asynchronous hypervisor job has stopped.

The internal HyperVComputeExecutor now combines dispatch verification, journal capacity/identity records, protected workload paths, verified image/runtime handles and the fixed driver. It is not a registered provider or transport endpoint. Deployment still requires independent lease enforcement, fenced asynchronous-job/orphan recovery, signed observations and confirmed storage teardown. Source images and payloads must be installer-owned protected paths. `ComputeCertifiedPayload` verifies a separate release signature, exact installed payload coverage and actual SHA-256 file content, and retains read-only handles without write/delete sharing. Keep those handles alive while consuming the image. The installed required-file manifest must include executable dependencies and come from trusted deployment configuration. No image or runtime has been certified by this implementation checkpoint.

Tests use a recording command runner for Hyper-V commands. Harmless real PowerShell tests cover bounded output draining and helper termination. Real VM creation, firmware, guest boot, isolation, resource enforcement, crash recovery and cleanup are not yet verified: this host has the Hyper-V module but the current account cannot query `Get-VMHost`, including outside the execution sandbox.

Command references: [Set-VMFirmware](https://learn.microsoft.com/en-us/powershell/module/hyper-v/set-vmfirmware?view=windowsserver2025-ps) and [Resize-VHD](https://learn.microsoft.com/en-us/powershell/module/hyper-v/resize-vhd?view=windowsserver2025-ps). Local command metadata was also inspected; hardware acceptance is still required.

Executor checkpoint: a verified provisioning claim creates a VM in a generated environment directory with a private OS disk, rechecks its signed authorization window, and activates it through the existing topology-validated start path. If creation consumes the authorization window, activation is denied and recovery only observes the stopped VM. Duplicate dispatches observe the recorded VM. If allocation completed before the response was lost, observation discovers the generated name, requires exactly one match with the complete ownership marker and records the recovered ID without another create operation. Ambiguity or ownership mismatch fails; a missing VM is only an inventory observation, never certified absence or teardown.

Start/restart revalidate the exact private disk, virtual capacity and standalone VHDX topology, CPU/static memory, Generation 2/Secure Boot template, absence of network/DVD/GPU/assigned host devices and checkpoints. Stop/destroy can remove an owned machine whose topology needs repair without requiring activation validation. Destroy retains private disks and reservations pending separate authorized storage cleanup. Platforms lacking a required inspection command fail activation rather than silently omitting the check.

Integration tests exercise signed dispatch, real release/file verification, durable journal recovery, initial activation and a recording Hyper-V command runner. Four additional tests parse the fixed command scripts in the real PowerShell helper without invoking them. This is not physical acceptance. The executor queues signed-result evidence through its journal: a Running VM maps to Bootstrapping, never Ready. A lost create or activation response leaves the execution fence intact; replay discovers or observes the owned VM without repeating creation or startup. Initial dispatch intake with configured certified templates, guest readiness, bounded guest execution and certified storage teardown remain required before rollout.
The executor also has a local lease-enforcement path requiring no fresh Core dispatch. The journal supplies protected original scope, exact resource identity, lease and the permitted cleanup action. Expired ephemeral VMs are destroyed; persistent VMs are stopped, preserving their disks. Unknown identity uses full-ownership discovery. Failure retains the expiry fence and reservation for retry; a Missing result still does not prove that disks or late jobs are gone. This path has simulated-backend tests for persistence, retry and clock rollback. Resident scheduling and real hardware acceptance remain unfinished.
Resident monitor composition is now available through CreateLeaseMonitor. The executor sends coalesced hints after journal-backed dispatches; the monitor always reads persisted leases, scans immediately on startup and uses deadline timers plus periodic recovery for lost hints. Its callbacks invoke the local lease-enforcement path. The service host must run and supervise this monitor and handle its bounded diagnostics. No service has been installed or started, and maintenance audit delivery and confirmed storage cleanup remain unfinished.
## Maintenance process entry point

The project now builds an executable as well as a test-referenceable assembly. Its `maintenance <absolute protected configuration path>` command loads ComputeProviderConfiguration version 1 and runs existing-lease recovery with queued HTTPS audit delivery. It requires an already initialized protected journal. It does not initialize/reset history, accept dispatches or expose a network listener. The maintenance executor has no provisionable templates or payload resolver.

Certificate opening is deferred until evidence needs delivery. Credential access/validity failures discard the cached certificate/transport and retry with the existing capped backoff while lease recovery continues. Every reopen selects the same configured thumbprint and enrolled public key; repairing access to that credential can recover delivery without restarting maintenance. An expired certificate cannot be replaced by an arbitrary store certificate. Both credential and transport outages emit `maintenance-delivery-retrying` when entering backoff and `maintenance-delivery-recovered` after successful delivery. Unexpected faults still stop the lane and emit `maintenance-delivery-stopped`. Per-pass lease failures emit `lease-maintenance-failed`. Fatal startup/monitor failures produce `compute-maintenance-host-failed` and exit 1; invalid usage/platform exits 2; Ctrl+C joins both workers and exits 0. Diagnostics use fixed codes without configuration, credentials or raw provider exception text. If diagnostic reporting fails, both workers are still cancelled and joined before transport/certificate disposal.

The `maintenance` command is a console process. The separate `service` command now integrates with Windows SCM and refuses interactive launch; no service has been installed by this work. Protected installer setup, service registration/recovery, explicit enrollment/certificate rotation without interrupting cleanup, dispatch/result transport, desired-state boot and real-host acceptance remain required. Tests run host composition against simulated Hyper-V and injected credential selection; no production host has been launched against real workloads.
## Windows service lifetime

The `service` command uses the repository-pinned Microsoft.Extensions.Hosting.WindowsServices 10.0.9 and service name `CSweet.Compute.HyperV`. It reads only `%ProgramData%\CSweet\Compute\provider.json`; command arguments, environment variables and appsettings cannot replace enrollment. Host defaults are disabled. Configuration loading and maintenance run inside the hosted worker. Service stop cancels and joins maintenance with a three-minute host shutdown allowance. Unexpected completion or fatal maintenance failure sets both failure state/process return code and the Windows service exit code to 1, emits a fixed-code critical log and requests host stop. Credential/network backoff remains inside maintenance and does not stop the service.

The installer must configure restart actions and enable actions for non-crash failures so a reported stopped state with nonzero service exit code qualifies for recovery. This follows the [Windows failure-actions flag semantics](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/ns-winsvc-service_failure_actions_flag). The wrapper uses the standard [Windows service hosting integration](https://learn.microsoft.com/en-us/dotnet/core/extensions/windows-service). Registration, protected deployment, Event Log source permissions, boot/restart acceptance and actual SCM stop/exit status still require installer and hardware validation. Current tests use the real generic host lifecycle without registering a service.
## First-install preparation and registration

Prepare a published runtime in a trusted protected directory, the protected journal/workload directories, and `%ProgramData%\CSweet\Compute\provider.json` using the version 1 configuration described in the runtime README. The service requires LocalMachine My certificate selection; a certificate in the installing user's CurrentUser store is rejected. The installed key must also be accessible to LocalSystem. No command here creates keys or opens network access.

`CSweet.Compute.HyperV.exe initialize-journal <absolute protected configuration path>` explicitly initializes a fresh journal through the existing guarded initializer. Existing valid history is preserved; missing/corrupt previously initialized history is never reset. Normal maintenance, service startup and validation never initialize history.

`CSweet.Compute.HyperV.exe validate-service` uses the fixed service configuration, verifies every installed runtime entry's protected path, reads the existing journal, opens the enrolled signing key and performs read-only Hyper-V inventory access. This validates the invoking installer's access, not proof of LocalSystem key access or guest isolation.

`scripts/Install-ComputeMaintenanceService.ps1 -ExecutablePath <absolute published executable path> -WhatIf` previews registration without changing service state. Running it without WhatIf requires elevation, refuses an existing service, verifies runtime ownership/ACLs/links before executing preflight, registers a stopped Manual LocalSystem service, configures restart delays of 60/120/300 seconds with non-crash recovery, then enables automatic startup. It does not start the service. A partial registration failure leaves the stopped Manual service for explicit inspection; reruns do not replace it. Installer runtime publication/configuration provisioning, actual SCM registration/start/restart, Event Log and LocalSystem key permissions still need deployment acceptance. This checkpoint only parsed and dry-ran the installer.

The internal host composition now supports optional dispatch intake with a separately owned work connection and fixed dispatch-intake-retrying/recovered/stopped diagnostics. Intake failures remain independent of lease cleanup; shutdown joins intake before disposing its connection. Public maintenance/service startup still disables provisioning until protected catalog/settings composition is supplied. Tests cover missing enrolled credentials with intake both enabled and disabled.

## Provisioning composition

The maintenance and SCM entry points now support the optional provisioningSettingsPath field described in the runtime README. A valid installed catalog enables the host's separately supervised dispatch intake and supplies certified templates/payloads to the executor. Omitted or unavailable settings preserve maintenance-only behavior; rejected settings emit a fixed diagnostic and never enable provisioning. Catalog contents are loaded once, while release expiry and actual payload bytes are rechecked on each provision. Changing installed settings requires restart. This supersedes the earlier checkpoints saying the entry points always disable intake. Durable remote wake subscription, guest readiness, complete teardown and hardware acceptance remain outstanding; the intake worker currently uses bounded startup/reconnect discovery and its local wake hook.

When provisioningSettingsPath is configured, validate-service also requires valid provisioning settings and certifies the actual installed runtime directory's complete flat file set plus every catalog image. Extra files, nested runtime directories and altered payload bytes fail preflight. This explicit installer gate does not use startup's maintenance fallback and does not create VMs. The current certificate schema supports flat runtime file names only.


Provisioning-enabled hosts now run a separately supervised authenticated notification connection. Core publishes durable outbox hints to the exact enrolled node; received hints wake intake, which performs current discovery and fresh claims. Notification outages use capped backoff and do not stop lease cleanup or bounded discovery. Shutdown joins notifications before disposing their connection. Fixed diagnostics use provider-notification-retrying/recovered/stopped. This supersedes earlier notes saying remote wake subscription is uncomposed; installed/hardware acceptance remains outstanding.


Provisioning composition now uses CSweet.Isolation.HyperV 0.1.0 as a pinned package for exact-VM guest sockets, on fixed service port 2763 with a three-second connect limit. It supplies the generic readiness probe; a successful response is followed by a second owned-VM Running observation before Ready is recorded. The package was locally packed for development validation, not published. Host service registration and a compatible generic guest responder are still required; no live socket or guest was installed. A missing guest remains Bootstrapping.

## Guest socket registration

Before provisioning-enabled service preflight, an elevated installer can run scripts/Register-ComputeGuestService.ps1. Use -WhatIf to inspect its fixed registry target first. The command registers only compute's port-2763 service ID, 00000acb-facb-11e6-bd58-64006a7986d3, with ElementName C-Sweet Compute Guest. It leaves a matching registration unchanged and refuses conflicting existing metadata. It does not start a VM/service or alter Office's port-2761 registration. A partial failure requires inspection; the script does not overwrite an unexpected key on retry.

validate-service now reads this exact registration when provisioning settings are present and fails on missing/conflicting metadata. Maintenance-only configuration does not require this guest channel. The script has only been parsed and run with -WhatIf during development; actual registration and Hyper-V guest connectivity still need installed-host acceptance.
