# Recover an expired, never-verified managed authorization

The account page can offer **Reconnect with fresh consent** for the original human's unverified administrative account grouping when its failed initial import has no resources or business grants, its original consent window and recovery grace have elapsed, and a read-only service snapshot confirms the old authorization is Revoked. Current package, profile binding and permission sets must still match. A status read does not create consent, credentials, grants or another import attempt. Missing, changed or unavailable authority keeps recovery unavailable.

The action opens the existing consent review with the original permission sets locked. The human must review and continue to the provider. `BeginManaged` independently repeats eligibility and permission checks; UI flags cannot authorize access. A successful new import verifies the newly selected provider account/resources in the same grouping without invoking Disconnect or erasing historical account data. Because the old account was never verified, this does not prove the human selected the same provider identity as before. Review the actual imported channel/resources before separately granting any business or agent access.

Retirement sends the existing signed supersede request for the exact old/new service connections. Core accepts a matching `Superseded` or `Revoked` acknowledgment with no scope grants; an error, wrong ID or pending status retains the old protected context for durable reconciliation. It never falls back to provider revocation. The new service independently verifies expiry/erasure provenance, same deployment/installation/actor/profile/package/policy/scopes and a fresh verified replacement. The old revoked record remains terminal. Previously verified or partially discovered revoked identities remain unsupported and fail closed.

The existing `external:managed-service-backups` provenance reference is retained. Clearing the retired live authorization context is not a claim that historical backups were erased. No deletion job, fake receipt, account reset or automatic policy restoration is introduced.

Adoption requires review and deployment of the paired service fix first, followed by the Core update. Protocol 0.5.0 remains unchanged; no package publication or database migration is needed. Source tests/draft PR publication do not authorize deployment, a debug restart, live recovery, Google consent, new scopes or business/agent grants. Existing keys, service selection and local settings are preserved.

Tests exercise the actual account service and rendered consent page with synthetic gateways. They cover read-only eligibility, original-human/package/profile binding, unchanged permissions, denied/pending service state, durable retirement receipts and retained backup obligations. Service integration tests separately exercise real HTTP routing, SQLite transactions, replay/ownership guards, rollback and replacement-fence races without live provider credentials.
