# Connection service onboarding and owner pilot

Local implementation based on the PR44/PR45 stack. Protocol package 0.4.0 is required; this is not a deployed release.

`ConnectionServiceSetupStep` is shared by first-run setup and Managed Connections Settings. Official, SelfHosted and Skip are optional. Choosing Official pins `ManagedServiceTrust.OfficialOrigin`; an advertised capability does not establish trust or grant authority. `ConnectionServiceSelectionStore` stores revision-fenced choices in SystemConfiguration, preserves an existing configured installation, and keeps its protected customer registration for cleanup when skipped. Existing completed installations remain complete. Interrupted setup resumes the saved choice; Back leaves the last saved choice intact. Unavailable services do not block local setup.

`/service-info` is a bounded capability probe. OAuth account setup/resource import is the pilot capability. Mobile pairing and general remote provider actions are disabled regardless of remote claims. The MAUI shell is not a pairing client.

`ConnectionServiceAdministrationEndpoints` requires the Identity application session, revalidates the security stamp and current database administrator role, and requires antiforgery validation for every write. The actor is obtained from the current session, never submitted by the browser. `ConnectionServiceOwnerGateway` exposes typed operations only and signs them using a separate protected owner registration. Backend signatures attest that the bound server checked its user; they are not independent human approval or protection from compromise of that server.

An operator must configure a separate absolute `CSweet:ConnectionServiceOwner:RegistrationPath` under protected application storage and preserve the existing Data Protection key ring. In Settings select SelfHosted and the exact HTTPS service origin, then explicitly prepare owner binding. This creates a separate local protected key and returns public bootstrap details. Review those details at the service machine and use its local `--owner-admin` command. Customer enrollment alone never grants service administration. Service-owned grants name the bound installation/user GUID, explicit capabilities and tenant scope. Global credential/package administration requires explicit global scope. The UI bootstrap proposes global authority and clearly labels it; the local operator can reduce it before applying.

Use the owner panel to import a provider credential document, approve a reviewed connector package manifest and enroll customer deployments. Credentials remain in request memory and encrypted service storage; responses/audits contain no credential document. Enroll responses contain identifiers only, used by the existing customer deployment pairing flow. No account passwords/databases are shared.

Recovery is performed at the service host: revoke a user grant or binding with its current revision, then grant a replacement user or bootstrap a fresh binding. If the owner installation is offline, local service administration still works. Revoke the old binding before archiving its protected registration and preparing a replacement; never edit the origin or revive its key. Keep customer registrations required for pending revocations.

Migration limitation: changing the origin of an already paired customer is deliberately blocked. There is no automatic transfer of account grants or key authority. A reviewed retire/cleanup/archive/re-pair workflow is still required before this feature supports that migration. Do not delete a registration to bypass the guard while cleanup remains pending.

Before deployment: review service bootstrap/grants, secret storage, callback/provider configuration and TLS routing separately. Current source changes do not configure any of these. Live YouTube consent and full UI acceptance remain required.

## Network policy

`CSweet:ConnectionServiceNetwork:AllowedOrigins` is an operator-managed list of exact canonical HTTPS origins. Its default permits only the official origin. Add a self-hosted origin explicitly in server configuration before connecting; choosing a URL in the UI does not edit this policy. `PrivateNetworkOrigins` is a separate explicit opt-in list for permitted internal origins and must also be included in AllowedOrigins. Private, loopback and link-local destinations are otherwise rejected after DNS resolution. The connection callback connects directly to the checked address and preserves normal TLS hostname/certificate validation; redirects, cookies and proxies are disabled. This policy applies to owner requests, capability probes and customer traffic, including cleanup. Preserve the old allowed origin while cleanup remains pending. Do not grant private-network exceptions to origins you do not operate. No live policy is configured by this change.

## Protocol package consumers

Protocol 0.4.0 adds `OwnerProtocol`, typed owner request/response records, `OwnerAdministrationClient` and `ConnectionServiceCapabilities`; existing customer wire version stays 1.0. C-Sweet Infrastructure needs the new package because the owner gateway and capability reader compile against those types; API and their tests consume it transitively. Service OAuth uses the sibling protocol project and is released/tested together. `tests/ProtocolConsumer` is pinned to 0.4.0 and checks owner signing/contracts/body deadlines through the packed NuGet artifact. The paused OIDC helper and earlier consumer scratch checkout remain at 0.3.0; neither needs the additive owner API. The YouTube connector itself declares SDK-managed operations and does not need a protocol bump merely to use unchanged customer OAuth. No package was published.

## Paired-origin migration blocker

A safe complete flow must freeze new attempts, cancel pending consent, revoke provider grants and await authoritative cleanup completion, preserve local business-data cleanup obligations, durably archive the old protected registration, then create a fresh key/binding for the new origin. Today `DeploymentAuthenticator` rejects revoked deployments before cleanup reads and the protocol exposes no retirement completion receipt. Simply revoking and deleting/moving the key would strand pending cleanup. The current UI therefore supports skip/change choices before pairing and skip/re-enable on the same paired origin, but blocks paired origin transfer. A retirement protocol/state-machine change and crash/concurrent-attempt tests are required before promising unrestricted change-later migration; do not bypass the guard manually.
