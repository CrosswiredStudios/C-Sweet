# Standalone Office onboarding

**Implementation plan and release status · November 24, 2026.** This plan covers a person installing Office on a computer they own and connecting it to managed or private Headquarters. The installer and browser are the ordinary user interfaces. The same design also covers an installation started in Headquarters. The canonical hosted account issuer is `https://account.c-sweet.com/`, already configured by `HostedAccountOptions`, `MobileAccountOptions`, and the hosted deployment bootstrap.

The journeys below define release acceptance. In this version, local resource review happens immediately before OS installation. Remote approval shows the computer, matching code and destination. A QR opens the approval URL. The matching code is for comparison across the two screens.

### First platform trial

Merge and publish Office.Contracts 0.15.0 first, and confirm a clean runner can restore it. Then merge the consumers with green CI and apply the Headquarters and Market migrations in staging. In CSweet.Office run `signed-release` on `main` with `package_only` enabled. This builds Windows x64, Ubuntu x64 and ARM64, and macOS Intel and Apple silicon installers. Download the per-platform Actions artifacts and the checksums from `release-metadata`. The run requires the configured hardened signing runners and skips GitHub Release publication.

Use a private Headquarters for the first clean install on each platform. Verify that this device receives an authenticated heartbeat, runs an isolated assignment, and keeps its identity after reboot. Repeat on a managed staging tenant with an available device slot and a reachable TLS gateway. Also test a Headquarters-issued code on a second computer and reopen an existing Office. For the unpublished Windows installer, keep all cabinets beside the MSI. The Office release guide covers testing the Setup EXE with cached assets and then testing a clean public download.

### Managed gateway rollout

`CSweet.Hosting/linux/bootstrap.py` reads optional guest configuration from `/etc/csweet-hosting/office-gateway/gateway.json`. Provision the tenant's `office-<deployment UUID without hyphens>.c-sweet.app` hostname. Route external TCP port 443 through to port 7443 on the assigned IPv4 bind address, preserving TLS and the client certificate until the Execution Gateway. The web tunnel serves the Headquarters browser.

Place `tls.pem`, `tls.key` and `office-issuer.pfx` alongside the configuration with restricted ownership and permissions. Set `hostname`, `bindAddress`, `issuerPassword`, `certificationSuite`, `builderDigest` and `runtimeDigest` using the tenant's credentials and certified image digests. Run guest bootstrap to render Compose. From the deployed Compose directory, run `python3 /path/to/bootstrap.py verify-office` using the installed script path. This checks public TLS, HTTP/2 and the tenant's assignment verification key. Complete acceptance by enrolling an external Office, verifying its certificate-authenticated heartbeat and running an eligible assignment. Configure `AccountIssuer:OfficeAppleAppId`, `AccountIssuer:OfficeAndroidPackage` and `AccountIssuer:OfficeAndroidSigningFingerprints` using the signed app identities.

## The first five minutes

| Where the user starts | What they see | What counts as success |
| --- | --- | --- |
| Fresh Office, managed Headquarters | The installer opens **Welcome to C-Sweet Office**. Choose **C-Sweet hosts my Headquarters**, then **Sign in with C-Sweet** or **Use my phone**. Display the proposed sharing limits with an optional **Adjust limits** action. Select the only eligible Headquarters automatically. Show a chooser when several qualify. The account confirmation names the computer, Headquarters and resources. | One **Link this Office** confirmation links the device and completes eligible fleet approval. Office displays the named Headquarters and its first authenticated health check. A person with no eligible Headquarters, no management permission or no available slot gets a specific next step. |
| Fresh Office, private Headquarters | Choose **I host my own Headquarters**, enter the familiar Headquarters HTTPS address, and approve the named computer in that instance as a local administrator. Offer **I have a connection code** for an enrollment already issued by Headquarters. | Private Headquarters issues the Office identity. Installation and approval work on a private network with cloud account services unavailable and the required installer assets already on hand. |
| Headquarters first | **This machine**, **Another machine**, a combined Windows install, and hosted **Your offices → Connect a device** keep their entry points. The local page recognizes the pending handoff, approved allocation or existing device. | Following either screen, opening a second tab, or restarting the service produces the same Office, approval and slot consumption. An enrolled device opens on status. |

**Phone behavior.** A hosted QR opens a short-lived HTTPS approval request at `account.c-sweet.com`. A supported installed app can open it directly. A signed-out user resumes that exact request after sign-in. The phone browser offers the same approval when the app is unavailable. Both screens show a matching code. The Office page updates when Headquarters accepts the link. A private QR opens the private instance’s own verification page on a phone that can reach it, for example over Wi-Fi or VPN.

## Phase 0 · Make the existing remote journey a reliable baseline

- **Office and Market** inventory actual release assets by OS, architecture, signing channel and required companion files. Use a platform-specific installer link where available. Show a clear availability message if a production installer is missing. For Windows, handle MSI cabinet companions through one guided download/install experience. Keep the automatic Windows development bundle and the hardened production release channels distinguishable.
- **C-Sweet** fix the download fallback that can send a user to a manifest instead of an installer. In `AgentHostOnboardingStep.RemoteExperience`, track the Office being added. Its current fleet-wide `IsReady` branch can show success for device A while the user is trying to add device B.
- **Hosting and C-Sweet** provision a tenant-specific HTTPS gateway, advertise it via `CSweet:ExecutionGateway:PublicUrl`, and configure the certificate issuer, signing keys and eligible image policy. Select an ingress design that preserves authenticated Office client certificates and long-lived HTTP/2 gRPC streams. Verify the path on the actual hosting edge before choosing the deployment recipe. Record gateway readiness separately from the hosted web readiness probe. Plan deployment for newly provisioned and existing tenants.
- **Exit evidence** from a clean computer on another network: install, use today's one-use code, approve in Headquarters, reconnect after a restart, and complete one signed workload. Add a second Office while the first is healthy. Also record the self-hosted baseline. A deployment whose fleet release policy limits work to its combined Office should explain that restriction even if a separate device enrolled.

## Phase 1 · Install first, connect later

- **Office** split platform setup into installation and enrollment. Install the software, establish local privilege boundaries and start Node in an explicit **Waiting for setup** state. Today Node expects enrollment material, Windows initially registers Node for manual startup, and the Unix configurators require the gateway address. An unpaired Office must be able to wait through a reboot without prompting, claiming an enrollment or accepting workloads.
- Serve the same Aurora and Gold pages from unprivileged **Office Node**. The interactive installer opens **C-Sweet Office** in the signed-in user’s browser. A Start menu, Applications, or Linux desktop launcher reopens it without requiring a port number. If Node is stopped, the launcher offers the OS-authorized **Start Office** or **Repair** action. Package UI assets with Office so the welcome page and local diagnostics work offline.
- Bind the page to loopback only. Authenticate the local operator through the launcher and a short-lived, OS-user-bound session. Enforce origin/host and request-forgery checks on changes. Use the established privileged installer/helper for protected service, storage and initial trust changes. Update Office’s network-surface documentation to describe the new loopback listener. Preserve RuntimeHost’s existing process boundary.
- **Exit evidence** on Windows, Ubuntu and macOS: open a clean install with no HQ details, quit and reopen, reboot and resume. Exercise an existing assisted setup, an enrolled Office and an unreachable HQ. Each opens the correct screen. Another machine or an unauthorized local user cannot change the link.

## Phase 2 · Deliver private onboarding and the shared pairing protocol

- **Contracts and C-Sweet** define a versioned discovery document served by the Headquarters web origin. It identifies the instance, advertises its verified gateway, approval origin and supported pairing methods. Accept an IP address when its HTTPS certificate covers that IP. Preserve the existing HTTPS gateway plus one-use-code path for older Headquarters.
- **Office and C-Sweet** bind a pending pairing request to the Office’s locally generated key, destination installation and proposed resource allocation. The local administrator signs in at their own Headquarters, checks the machine and matching code, then approves once. Enrollment uses the existing CSR, fleet qualification, certificate issuance, trust pinning and authenticated heartbeat. On private-CA installs, provide a platform-appropriate trust check and a useful error for a wrong name or fingerprint.
- Persist pending state and approval durably. Commit state changes with their notification outbox entries. A notification wakes the waiting UI or device, which reads authorized current state. Provide a bounded status read for missed events or restart. Make redemption proof-of-possession bound and idempotent, including loss of the response after HQ accepted the claim. Expire or cancel an unused request. A QR carries only a verification link and public matching code. Device redemption material stays on the installing computer.
- Keep an existing guided session’s correlation, allocation and approval. Bind progress to the exact enrollment/device. Display **Awaiting approval**, **Approved, connecting**, **Connected**, and **Ready for work** from their respective facts. Loss of connectivity displays the last known connection and time. Relinking an enrolled Office is an explicit administrator action that respects active work and revocation.
- Use the pending session ID and verified Office key to resume a known enrollment across entry points. A friendly device name is display text. When a user supplies a valid HQ-issued code, adopt that reservation before attempting to allocate another. A competing request with a different key must get a distinct decision.
- **Exit evidence:** desktop private URL, private phone browser and existing code all work with Market unreachable. Exercise certificate mismatch, expired/canceled code, duplicate approval, concurrent claims, wrong machine/key, lost acknowledgement, restart, and revocation. Two Office machines receive distinct identities.

## Phase 3 · Link to managed Headquarters through the hosted account

- **Market** add an Office-specific client/scope and device verification page to the configured account issuer. Reuse C-Sweet sign-in and eligible workspace records. The existing Headquarters registration client links an installation to Market; it conveys a different authority from adding an Office to a particular tenant. For desktop sign-in, preserve the pending Office request across authentication. For headless or phone approval, expose the same intent through a verification URL and short code. [Device authorization interaction](https://www.rfc-editor.org/rfc/rfc8628.html#section-3.3)
- **Market and C-Sweet** resolve only managed instances this account can add devices to. Preselect one eligible instance and offer a chooser for several. The confirmation names the destination and machine. With no eligible instance, explain how to obtain administrator access; with no free slot, point the authorized user to **Your offices**. An ordinary Office sign-in must never trigger a purchase.
- **C-Sweet** factor the existing hosted management permission and serializable slot reservation out of `HostedOfficeEndpoints.EnrollDeviceAsync` for both entry points to use. At approval, recheck the signed-in subject, tenant, permission, entitlement, expiry and device-key binding. Exchange a short-lived tenant-scoped authorization for the normal fleet enrollment. Headquarters owns approval and the operational certificate. Record the approving account for audit. One retry or a desktop/phone race consumes one slot and produces one Office. Release unused reservations on expiry or cancellation.
- **Office** resumes the same pending request after browser sign-in without storing a password, account session or refresh token. Transition to connected only when the target HQ acknowledges the exact device and its authenticated connection arrives.
- **Exit evidence:** run against a managed tenant using `account.c-sweet.com` and a real external Office. Cover one/multiple/no eligible Headquarters, lost permission, wrong tenant, full slots, two users competing for the last slot, simultaneous initiation from HQ and Office, and a browser closed after approval. Show one approval, one device, and the correct quota after retry.

## Phase 4 · Finish the phone journey

- **Market** publish an HTTPS Office-verification route on `account.c-sweet.com` and the iOS and Android domain-association records for the shipped app identities. The same URL must work in a browser before the app integration is released. Offer a typed verification code as an accessible alternative.
- **C-Sweet mobile** handle verified links on cold start and warm resume in `CSweet.Maui`. Use `MobileAccountSession` for sign-in. Preserve the pending request through the sign-in callback, account switching, and app suspension. Show the target computer, destination Headquarters and matching code on the phone. The existing phone-to-HQ device enrollment is a separate identity. Private HQ addresses continue to support an ordinary browser on a reachable network. [Apple associated domains](https://developer.apple.com/documentation/xcode/supporting-associated-domains) · [Android App Links](https://developer.android.com/training/app-links/verify-android-applinks)
- **Exit evidence:** on physical iPhone and Android devices, scan from a fresh Office with the app installed and signed in, installed and signed out, and absent. Test decline, expiry, incorrect account, duplicate scans and browser fallback. In every success case the original waiting Office advances automatically.

## Phase 5 · Complete local management and release

- **Office** add local status, current work, sharing limits, storage, sanitized diagnostics and support-report preview. Distinguish an unavailable HQ from a stopped service, an untrusted certificate or an uncertified workspace. Show freshness when offline. Safe local changes identify the required OS permission. Connected actions such as pause/drain, update, repair and disconnect use established HQ authority and retirement rules. Tell the user when a running task must finish and verify the resulting state before showing success.
- Ship a Windows tray entry, macOS menu-bar entry and Linux desktop indicator where supported. They show status and open the same page. The ordinary app launcher stays available on desktops without an indicator. Logging out of the desktop keeps the services running. Preserve existing protected-input provisioning for headless administrators.
- **Release order:** publish any additive Office.Contracts minor version first. Bump its project version, update both consumers’ pins, build/test/pack, verify the actual `.nupkg`, and validate C-Sweet and Office with `UseLocalOfficeContracts=false`. Deploy backward-compatible HQ, gateway and account support before advertising the Office-first buttons. Release signed Office artifacts per platform, verify the public download and clean install, then enable hosted availability per qualified tenant. Native app links can ship afterward using the working browser fallback.
- **Rollback:** disable creation of new pairing requests for the affected path; finish valid pending sessions or show explicit expiry. Keep prior installed identities, certificate renewal/recovery, existing assisted setup and manual codes usable. Use the normal signed Office maintenance/update path for installed devices.
- **Release evidence:** retain OS, Office/HQ versions, immutable asset, ingress path, exact Office ID and workload outcome for each supported journey. Extend `ExecutionFleetServiceTests`, hosted browser and Office installer/identity tests, and `MobileShellTests` at their public boundaries. Where changes affect agent execution pickup, run a deterministic `Category=AgentHarness` journey from the public callback through the actual assigned worker lease. Record its name, case count and observed result separately from hardware acceptance.

## Office README deliverable

Start the rewrite in Phase 0, alongside the download fixes. Publish instructions for each new flow with its first verified release. **CSweet.Office** owns the operator instructions; Headquarters and Market link to the corresponding section.

1. **Introduce Office in two sentences.** “C-Sweet Office lets this computer run work for your team. Connect it to Headquarters hosted by C-Sweet or to a Headquarters you run yourself.”
2. **Put downloads first.** Provide a short Windows, Ubuntu and macOS table with architecture, hardware prerequisites, signed installer and companion assets, or a clear availability status. Label development bundles and their required host certification. Link the independent source build and platform-specific payload installation guides separately.
3. **Offer two quick starts.** For hosted, install → open Office → **Sign in with C-Sweet** or **Use my phone** → confirm the named Headquarters → verify the device. For private, install → **I host my own Headquarters** → enter the secure address or use the issued code → approve locally → verify the device. For an installer launched by HQ, say “Open C-Sweet Office to see setup progress.” Include screenshots in Aurora and Gold when the screens ship.
4. **Define done and offer recovery.** Show how to recognize *this computer* in both places, check its first authenticated contact, and distinguish connected from eligible to run work. Point the reader to local diagnostics for gateway address, TLS, slot, approval or virtualization problems, and to the launcher when the service is stopped.
5. **Move history below the operator path.** Move the stale “unpublished 0.8.0” material to historical references. Correct the platform claims for automated development bundles and describe Headquarters-authorized Windows maintenance. Keep the source quick start explicit about the difference between building the independent solution and installing a certified payload.

**Definition of done for the README:** give a fresh-machine tester only the public README. For each advertised OS and hosting path, they can identify the right asset, install it, link the intended Office without opening a terminal on a desktop installation, and tell whether it is ready. Check download links against the actual release manifest/assets and repeat the trial for an already-enrolled computer.
