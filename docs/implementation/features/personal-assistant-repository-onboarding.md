# Business-first creation and project imports

## Business creation and destinations

`NewBusinessDialog` navigates both choices to `NewBusiness.razor` at `/businesses/new`, carrying `mode=New` or `mode=Existing`. `BusinessOnboardingService.StartAsync` persists `BusinessOnboardingOperation.StartMode` alongside its stable creation key, organization and owner. Missing modes default to New. Retried and background operations retain the saved destination: New opens Overview; Existing opens `/organizations/{id}/onboarding`. GitHub, profiling, staffing and compute are independent of this commit.

`BusinessSuggestionService.EnsureChiefAsync` inserts a business-scoped `hire-chief-of-staff` suggestion in the creation transaction. No Chief is a successful creation outcome. Overview and `OverviewAttentionState` read the authorized pending suggestion queue. Browse links to the filtered marketplace without approving a hire; dismissal records the human owner/manager and clears it for the whole business. `CSweetDbContext.CaptureBusinessSuggestionsAsync` completes a pending suggestion when an actual active Chief assignment is saved. Stable keys preserve dismissal across imports and reloads.

## Reusable full-page import wizard

`ExistingBusinessOnboarding.razor` is linked from Overview and Projects. `StartBusinessImportAsync` binds an authorized legacy draft or resumes an unfinished business session. `BusinessImportsAsync` provides bounded recovery links. `FinishAsync` records that the user left the wizard without cancelling profiling, removing projects or losing review context; later imports can start another session.

New entries expose Codebase → GitHub. Authorized saved business connections and verified draft installations are reused. `RepositoryGitHubConnectionFlow` reuses configured platform apps or resumes pending platform setup embedded in the wizard. Registration and verification retain administrator, revision and callback-owner checks; retries do not register another app when saved setup exists. Connect GitHub uses the [GitHub App user authorization flow](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app), then discovers installations with the one-time user token instead of reopening the app installation selector. OAuth-only callbacks carry a code/state without an installation ID; `GitHubUserAuthorizationClient.ListAuthorizedInstallationsAsync` derives authorized IDs from GitHub and the trusted host verifies the configured app. Tokens are not retained. The separate repository-access link opens the saved app in another tab; after changing access, reconnect from the preserved wizard. This also recovers installations whose standalone setup return lacks the original draft state. OAuth callbacks return to the same business wizard. A callback nonce belongs to the user who started it even when several owners can access the business.

`AddProjectsAsync` verifies current repository access and commits each repository independently under business/repository locks. `ProjectRepositoryAssociation` and the canonical Proposed Workstream are saved together. Proposed imports appear as **Setup pending** with no fabricated manager, team, board or execution authority. A stable repository association reuses an existing project across sessions; cross-business repository conflicts remain unavailable. Failure of one source retains successful projects and the business. The GitHub commit downloads no code and invokes no model. ZIP archives saved by the older flow remain supported through compatibility endpoints and their replay-safe internal import receipts.

## Independent project profiles

Only after projects exist and explicit excerpt/model consent, `AnalyzeAsync` queues bounded snapshot preparation and durable Personal Assistant work. `ImportedProjectProfile` retains separate inferred and accepted JSON, revisions, requesting user, analysis session/work identity and acceptance attribution. Each profile contains purpose, category, technology, documented current state, uncertainties and exact snapshot/path evidence. Missing assistants, revoked access and download/model failures affect profiling alone. Owners can manually edit and accept profiles individually and leave/resume while analysis runs.

`RepositorySourceStore` retains its traversal/link/size checks and secret/generated/binary filtering. Code, hooks and builds are never executed. `RepositoryBriefValidator` validates source coverage and exact evidence. `PersonalAssistantResultObserver` verifies current ownership, work identity and analysis revision before applying a result. Validate the whole response before changing any profile; owner acceptance and newer edits win over late/duplicate results. Business identity and mission are never derived or overwritten by import analysis.

The Personal Assistant remains configured during first-run onboarding. This wizard offers no assistant setup detour. It uses the standard user-scoped SDK agent, signed build/isolation, encrypted inbox, configured model and normal runtime authorization. The historical company-brief wire envelope remains compatible, but its business identity fields are empty and are never committed to business data.

## Chief, managers and activation

Imports create no employees, installations or VMs and do not seed a fixed Chief/PM/Architect team. SDK `WorkstreamSummary.ImportedProject` exposes accepted context and pending profile status through authorized current-state reads. The Chief discovers imports on durable workstream-change wakes and bounded attention recovery. Accepted software profiles support dedicated project-bound PM recommendations. Unknown/unaccepted profiles remain incomplete context. Games retain the Director/Producer leadership path and its normal pitch, creative review and staffing gates.

`WorkforcePlan.AssignAsProjectManager` is frozen into the reviewed hiring snapshot. A successful approved compatible manager hire assigns the existing project and reserves the manager. Unreviewed recommendation resolution cannot grant this assignment. The PM asks for CEO direction and uses existing approved staffing, then proposes governed setup with `WorkstreamPlanProposalV2Request.ExistingProjectId` and `ExpectedProjectRevision`. `ImportedProjectAdoption` validates organization, revision, Proposed state and management; the managed-action executor adopts that same Workstream instead of creating another. Normal approval, staffing, repository, membership and execution gates remain required. One imported project per manager is enforced; shared managers remain deferred.

`BusinessSuggestionService.Queue` writes UI and durable agent wake outboxes atomically with project/profile changes. Events are hints, not grants. Agents re-read current state, use stable recommendation/proposal keys, and recover after missed/duplicate/out-of-order wakes. Overview links imported projects and remaining profile reviews. Unstaffed project views handle nullable team/manager identities explicitly.

## Compatibility and rollout

Legacy drafts without a business route to the details page to choose/create a business. Bound drafts resume their existing business. Old confirmation cannot create another business; old creation jobs fail recoverably with a resume instruction. Do not delete GitHub apps or connections automatically.

Apply the additive `BusinessFirstProjectImports` migration and callback-ownership/index follow-up through normal deployment migrations. Preserve the configured durable `RepositoryOnboarding:StagingPath` and saved archives. Publish Work Management Contracts 5.2.0 and SDK 5.9.0 before the manager agent releases; update agents through published releases and Installed Agents. Local test/publish output is verification, never an installed-runtime patch.
