# Progressive sprint continuation

`Production Sprint 1` task completion and aggregate delivery acceptance are separate milestones. The successor may start only after the current increment's independent reviews, manager acceptance and configured promotion gates complete.

## Confirmed failure chain

- Producer `ProgressivePlanning.AdvanceProgressivePlanningAsync` indexed every board title key. The manually retained release-QA Epic, Story and Task all had `[release-qa-follow-up]` titles without proposal provenance, causing `ArgumentException` and repeated-failure parking of the retained planning commitment.
- Producer `WorkflowStaffing.StaffWorkflowAsync` selected every detailed Epic, mixing deferred release verification with the active scaffold increment. SDK `HierarchicalProjectDelivery.PrepareIncrementAsync` correctly rejected that different scope.
- Platform `WorkDeliveryService.DispatchDeliveryAsync` enqueued the Epic review before its attempt/cursor were persisted. Runtime preparation's degraded-mode tracking reset could retain the inbox item while discarding the assignment's orchestration state. That untouched item could not be claimed and prevented redispatch.
- Owner-report requests could accumulate across changed incident hashes while earlier requests were still queued. Their FIFO order delayed production continuations.

## Corrections

Producer 3.2.5 uses `ProgressivePublishedItems` to index only provenance-bound keys from the accepted proposal. Unrelated follow-ups remain intact; duplicate authoritative identities produce an explicit planning blocker. `StaffWorkflowAsync` reuses the active/paused plan's exact Epic set and excludes manual follow-ups from subsequent increment discovery.

`ReadProgressiveContinuationAsync` rereads current canonical tasks and completed increment plans. `AuthorizeContinuationRecoveryAsync` records a revision-bound recovery receipt before requeueing an unexpected execution failure. A crash before requeue can resume the same revision; failure after requeue cannot receive another retry from duplicate notifications. Acceptance-dependent waits can wake after actual acceptance. Unchanged authority/planning conflicts remain parked, and timed discovery remains available after missed notifications.

Platform `WorkDeliveryService.PulseAsync` commits the stage, attempt, inbox and outbox before activating a runtime. `ResumePendingDeliveryDispatchAsync` can rebind an untouched historical inbox assignment only after current scope, candidate, principal, attempt, deadline and project authorization checks. It retains the original work and attempt identities. `CurrentDeliveryStage` uses the persisted stage key and greatest traversal, rejecting missing/ambiguous identities instead of relying on collection order.

`ProjectHealthService.RefreshOwnerReportsAsync` keeps one outstanding owner-report wake per incident/reporter across the outbox and inbox. `AgentWorkInbox.ClaimCoreAsync` serves other due work ahead of informational owner-report refreshes. Neither operation resolves incidents or changes reporting authority.
