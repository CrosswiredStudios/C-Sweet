# Build provider setup

`AgentImportPreviewResponse.ToolchainAdapters` carries the reviewed adapter declarations into the plugin installation screen. `AgentImportPreviewService.ToResponse` reads them from the immutable package manifest. The declaration, rather than a package-name exception, distinguishes a build provider from a communication service.

`AgentInstallationService.InstallCoreAsync` requires declared service toolchain providers to use one organization UUID and `OnDemand` activation. Ordinary service plugins retain their system/always-on policy. `Plugins.IsToolchainProvider` uses the same declaration to require business selection and preserve on-demand activation. Installation retains ordinary manifest, grant, package, configuration, resource and isolation checks; it creates no toolchain eligibility.

`ToolchainCertificationEndpoints.ReadSetupAsync` supplies the build-runner screen with exact active, enabled, built business installations, version-matched immutable definitions, and currently ready Office image digests. `SetupAsync`, existing certification start, listing and revoke routes remain inside `HostAdministration`. Start also checks organization scope and rereads current package, readiness and capacity.

`ToolchainSetup` at `/settings/toolchains` lets a deployment administrator select a business, provider, declared build environment and Office image, review the combination, and invoke the existing certification pipeline. Changing a selection clears review; an already running combination cannot be submitted again from the screen. The API remains authoritative. Each declared fixture runs twice and must satisfy the existing reproducibility checks before eligibility exists. The UI reports scheduled tests rather than claiming capacity or project execution.

`ToolchainSetupTests`, `ToolchainSetupPageTests` and `AgentInstallationServiceTests` cover organization boundaries, disabled/staged/unbuilt/version-mismatched providers, unavailable Office capacity, administrator route policy, exact reviewed request binding, duplicate prevention and unchanged communication-service behavior. The setup screen does not resolve CEO decisions, hire employees, or substitute for Technical Director feasibility and Director project selection.

`Plugins.InstallAsync` requests the existing first-party runtime minimum (1024 MiB) for publisher `com.csweet`; other services keep 512 MiB and broker-only connectors keep zero compute. The backend resource validator remains authoritative. `PluginSettingsTests.InstallRequestHonorsFirstPartyRuntimeMinimumAndKeepsConnectorsBrokerOnly` exercises actual reviewed installation requests for both publisher classes and service/connector modes.

`AgentRuntimeInstance.DeliveryBuildId` separates managed build runtimes from the ordinary installation loop. `UX_AgentRuntimeInstances_ActiveInstallation` applies only to ordinary runtimes; `UX_AgentRuntimeInstances_ActiveDeliveryBuild` retains one active runtime per build. The migration derives existing bindings from workload assignments and rejects ambiguous identities. `AgentRuntimeManager`, startup cleanup and interactive readiness exclude managed builds; Office assignment leases and confirmed teardown own their lifecycle.

`ToolchainCertificationEndpoints.QueueCertificationBuildAsync` serializes dispatch per build and atomically saves its runtime and workload assignment. Replayed dispatch does not create another runtime. `ExecutionBrokerSessionRunner.ValidateCertificationFixtureAsync` accepts packaged fixture source only for a current matching certification run, immutable definition, declared fixture, exact provider artifact and exact Office image; ordinary builds still require their organization repository.

`ResumeAsync` and the administrator screen's **Resume fixture dispatch** action recover partial dispatch using the saved run revision. They recheck current provider/image capacity and immutable inputs. Only pre-provider broker exhaustion with zero executed build attempts can be requeued; actual failed fixture execution and exhausted provider budgets are retained. This does not grant eligibility or waive reproducibility checks.

`ToolchainCertificationDispatchTests`, `ManagedToolchainRuntimePostgresTests` and `AgentRuntimeManagerTests.ManagedBuilds` cover four independent fixture runtimes, dispatch replay, exact fixture authority, recovery limits, PostgreSQL uniqueness and separation from ordinary agent scheduling.

`DeliveryEvidenceCapabilityHandler.HandleManagedProviderAsync` authorizes service callbacks without an employee record. It requires the existing per-capability grant, active organization-scoped built service installation, exact definition/package version, managed runtime/build binding and unexpired running Office assignment. Services can read only an explicit assigned build and use its existing claim, heartbeat and report paths; they cannot scan Workstreams or use employee planning, cancellation, preview or publication capabilities. `ManagedBuildProviderIdentityTests` covers all four callbacks and rejects missing grants, other builds/businesses, ordinary runtimes, expired assignments and inactive or mismatched packages.

`ExecutionWorkloadOrchestrator.FenceExpiredAsync` also fences active managed assignments whose exact build has a durable terminal provider report. The existing stop journal retains VM capacity until Office confirms teardown; failed results remain failed, and successful results retain their ingested artifact requirement. `ExecutionManagedBuildStopTests` covers terminal-result cleanup and leaves actively executing builds alone.

`ToolchainCertificationWorker.ManifestHash` reads the same web JSON convention used by provider report persistence. `ToolchainCertificationCompletionTests` exercises all four saved fixture records, matching versus mismatched or absent provenance, failed fixtures and replay-safe eligibility creation.

`Plugins.ReviewPublishedUpdate` reuses the existing import review for service installations without account declarations. A published bundle must match the installed package ID and business; approval uses `StageUpdateAsync` and `ApproveUpdateAsync` instead of creating an unrelated installation. Connector account updates retain their separate account cleanup/review flow. `PluginSettingsTests.PublishedServiceUpdateUsesTheExistingRevisionFlowAndExactReviewedScope` verifies review, package/business binding, published-bundle selection and preserved organization/on-demand settings.

`AgentInstallationService.UpdateAsync` recognizes that uploaded service bundle sources are content-addressed: the two built signed bundles may have different source rows only when their service/package/publisher identities match and both sources are `PluginBundle`. Staging still grants no authority. `ApproveUpdateAsync` requires the exact new bundle digest, which the reviewed import UI sends. Ordinary repository-source identity checks remain unchanged; account connectors retain their separate policy.

`WorkstreamPurpose.ToolchainCertificationProfile` identifies internal fixture build storage. `BusinessProjects()` excludes it from human project inspection, agent portfolios/workforce snapshots, project intake, Chief coverage inputs, project reporting, efficiency project lists, and project health discovery. Certification history and fixture evidence remain available through the Host Administration Build runners endpoints; no business team, sprint or hiring plan is created for certification.
